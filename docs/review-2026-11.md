## 1. Money

### R1. A credit note is capped by the bill's total, not by what was billed and not written off (High)

`src/BillingRecon.Application/Billing/CreditNoteCaps.cs:26`, `src/BillingRecon.Domain/Billing/CreditNote.cs:330`,
`src/BillingRecon.Application/Billing/ApproveCreditNoteHandler.cs:122`

The cap is `creditNote.Total + alreadyCredited <= bill.Total`. Adjustments on the bill are not part of it, and nothing
in the approval looks at them.

Sequence (one tenant, every step approved by a checker, each step valid on its own):

1. Clerk posts bill B for 1,000.00. Nobody pays.
2. Clerk drafts a write-off adjustment of 1,000.00 on B; supervisor approves. `B.BalanceDue = 0`, ledger
   `Dr Adjustments / Cr Receivable(B)`.
3. Clerk drafts a credit note of 1,000.00 on B; supervisor approves. The cap passes (0 credited so far, total 1,000).
   `toOwnBill` is 0 because the balance is 0, so the whole 1,000.00 stays as `AvailableAmount`.
4. Cashier drafts a refund of 1,000.00 from the credit note; supervisor approves. `Dr CreditAvailable / Cr Cash`.

The system now holds a cash refund of 1,000.00 to a payer who never paid anything. Every identity of
`docs/database.md` 5.5 still holds, so the reconciliation reports no drift. The same works in part (write off 400,
credit 1,000: 600 is applied to the bill, 400 becomes refundable).

Smallest fix: in `CreditNoteCaps.CheckAsync` subtract the posted adjustments of the bill from the cap
(`Total + alreadyCredited + adjusted <= bill.Total`), read through the Billing-to-Adjustments seam that ADR 0026
already has in the other direction, and re-check it at the second cap check under the lock (handler line 116). Add the
matching reconciliation row beside `CreditNotesExceedBillTotal`.

### R2. The same receipt recorded twice under two idempotency keys is two payments (Medium)

`src/BillingRecon.Application/Payments/RecordPaymentHandler.cs:33-86`,
`src/BillingRecon.Infrastructure/Payments/PaymentConfiguration.cs:64-80`,
`frontend/src/api/useIdempotentRequest.ts:25`

Recording a payment has no `If-Match` (there is no document yet) and no duplicate check: the only unique indexes on
`Payments` are the number, the series position and the legacy number. The key is kept in component memory only.

Sequence: cashier sends `POST /api/v1/payments` (UPI, reference `UTR123`, 5,000.00, key K1). The server commits, the
answer is lost (network, or the tab is reloaded). The form is filled in again; the hook makes a new key K2 because the
old one lived in a `useRef`. The server records a second payment `PAY/..` with the same payer, method, reference, date
and amount. The payer now has 10,000.00 of unapplied cash for 5,000.00 received, and either copy can be refunded.
Undoing it needs a payment reversal with a checker.

Every other "same action, two keys" path was checked and is stopped: actions on an existing document need `If-Match`
and the second attempt gets 409; the opening batch is stopped by its content hash; the party import matches by MRN.

Smallest fix: for methods other than cash, refuse (422) a second non-reversed payment of the same payer with the same
method and reference, with a filtered unique index `(TenantId, PayerId, Method, Reference) WHERE Reference IS NOT NULL
AND Status <> 'Reversed'` behind it. For cash, at least answer with a warning field when an identical payment of the
same user exists within a few minutes.

### R3. Idempotency keys are never swept, and a key orphaned in progress blocks its request for good (Low)

`src/BillingRecon.Infrastructure/Common/Idempotency/IdempotencyStore.cs:56-79, 131-151`,
`src/BillingRecon.Domain/Common/IdempotencyKey.cs:18, 110`

`ExpiresAtUtc` is written and indexed, and `CLAUDE.md` rule 10 says an expired key is deleted, but no code reads the
column: there is no sweep, and `DecideAsync` does not look at it.

- The reservation is committed in a context of its own (line 62) before the business transaction opens. If the process
  dies between that commit and `CompleteAsync`/`ReleaseAsync`, the row stays `InProgress`. Every retry with that key
  then answers 409 `idempotency_in_progress`, which the frontend treats as retryable with the same key
  (`useIdempotentRequest.ts:12`), so the user loops until the page is reloaded.
- The table (with the stored response bodies) grows without bound.

No money is wrong: the business transaction of the dead request was rolled back.

Smallest fix: in `DecideAsync`, treat an `InProgress` row older than a short limit (a few minutes) as abandoned: delete
it in the own context and reserve again. Add the sweep the index was built for.

### R4. The reconciliation has no document-side identity for a bill's balance (Low)

`src/BillingRecon.Infrastructure/Receivables/ReconciliationQuery.cs:104-107`

`PaymentAllocations` (line 146) and `CreditNoteApplications` (line 235) tie a cache to its documents. For bills there
is only cache-versus-ledger (`BillBalance`). A bill whose `BalanceDue` and ledger agree with each other but not with
`Total - active allocations - active credit applications - posted adjustments` is not reported. Today nothing
produces that state; the check is the net under a future change to any of the four writers of `Bill.BalanceDue`.

Smallest fix: one more `UNION ALL` row, `BillSettlements`, built like `PaymentAllocations`.

## 3. Authorisation

### R5. A TenantAdmin can be maker and checker alone, through user administration (High)

`src/BillingRecon.Api/Common/Authorization/Policies.cs:70-83`,
`src/BillingRecon.Application/Identity/CreateUserHandler.cs:33`,
`src/BillingRecon.Application/Identity/ResetUserPasswordHandler.cs:38`,
`src/BillingRecon.Domain/Common/ApprovalRequest.cs:175`

Maker-not-checker is a comparison of user ids. The TenantAdmin role holds every maker policy, the `Decide` policy and
`ManageTenant`, and creates users with a password of the admin's choosing, or sets the password of an existing one.

Sequence, one person, one browser:

1. Admin A drafts a refund of 50,000.00 from a payment and submits it (`POST /refunds`, `POST /refunds/{id}/post`).
   A is the maker.
2. A sends `POST /api/v1/users` with roles `[Supervisor]` and a password A chose (or
   `POST /api/v1/users/{id}/password` on an existing supervisor).
3. A signs in as that user, sets a new password at the forced change, and sends `POST /refunds/{id}/approve`.

The refund is posted: cash out on one person's decision. The same route approves A's own credit notes, adjustments,
reversals, prefix changes and opening batch. It is all in the audit trail, but rule 9 says the control is enforced, not
only recorded.

Smallest fix, in order of cost: (a) refuse a decision when the checker's user row was created, or had its password
reset, by the maker (`CreatedByUserId` is already stamped; record who reset the password); (b) better, take `Decide`
and the maker policies away from TenantAdmin so that user administration and money are different people, and say so in
the matrix.

### R6. The bill-posting approval threshold can be lifted by the person it is meant to check (Medium)

`src/BillingRecon.Application/Identity/UpdateTenantSettingsHandler.cs:31-37`,
`src/BillingRecon.Application/Billing/PostBillHandler.cs:78`

`PATCH /api/v1/settings` changes `PostingApprovalThreshold` at once, with no second person. TenantAdmin also holds
`WriteBills`.

Sequence: threshold is 100,000. Admin A drafts a bill of 900,000, sends `PATCH /settings` with the threshold null (or
higher), sends `POST /bills/{id}/post` (posted directly, number taken, ledger written), then `PATCH /settings` back to
100,000. A bill above the threshold is posted with no checker. Three audit records remain.

Smallest fix: make a raise or removal of the threshold a maker-checker request like a prefix change (the machinery of
`PrefixChange` fits), or refuse the settings change to a user who has bills in `Draft`/`PendingApproval` of their own
making; lowering it can stay direct.

### R7. The audit trail hands any role the full content of documents its role may not read (Medium)

`src/BillingRecon.Api/Audit/AuditRecordsController.cs:22-56`,
`src/BillingRecon.Infrastructure/Audit/AuditReadService.cs:21-22`

`GET /api/v1/audit-records?entityType=X&entityId=Y` is open to every role; only `User`, `Tenant`, `PrefixChange` and
`NumberSeries` are held back for TenantAdmin. Each record carries the before and after image of the whole row with its
children.

Sequence: a Cashier (matrix: no access to adjustments, not even reading) takes an adjustment id from
`GET /api/v1/reports/pending-approvals` (see R8) or from a bill's history and sends
`GET /audit-records?entityType=Adjustment&entityId=...`: 200 with amount, kind, reason and bill. The same gives a
BillingClerk every refund (`entityType=Refund`), and any role, Viewer included, the opening batches
(`OpeningBatch`, readable otherwise by `Decide` only), approval requests and print settings.

Smallest fix: in the controller, map each entity type to the read policy of its document
(`Adjustment -> ReadAdjustments`, `Refund -> ReadRefunds`, `OpeningBatch`/`ApprovalRequest -> Decide`, ...) and
authorise against it as is done for the four admin types; refuse an unknown type.

### R8. The pending-approvals report shows the checker's inbox to every role (Low)

`src/BillingRecon.Api/Reporting/ReportsController.cs:169-170`,
`src/BillingRecon.Infrastructure/Reporting/ApprovalReports.cs:83-128`

The inbox `GET /api/v1/approval-requests` needs `Decide`. `GET /api/v1/reports/pending-approvals` needs only
`Reports` (all five roles) and resolves each request to its document, payer and amount, across adjustments, refunds,
credit notes and reversals. A Cashier therefore lists pending adjustments, a BillingClerk pending refunds: blank cells
of the matrix.

Smallest fix: put the action under `Decide`, or filter its rows to the document types the caller's role may read.

### R9. The maker of a request is whoever pressed submit, not whoever wrote the document (Low)

`src/BillingRecon.Application/Payments/PostRefundHandler.cs:60-74` (the same shape in `PostBillHandler.cs:109-120`,
`PostCreditNoteHandler.cs:64-75`, `PostAdjustmentHandler.cs:63-78`)

`ApprovalRequest.MakerUserId` is the caller of `/post`. The user who drafted and last edited the amounts is not
compared with the checker.

Sequence: Supervisor S drafts a refund of 80,000.00 (`POST /refunds`). Cashier C, asked to "send the ones in draft",
submits it. S approves: S decided the payee and the amount and S approved them. Two people were involved, so this is
weaker than R5, but the person who chose the amount is the checker.

Smallest fix: refuse the decision when the checker is the document's `CreatedByUserId` or `UpdatedByUserId` as well as
when it is the maker.

## 4. Input

### R10. Legacy numbers and guarantor references are compared case-sensitively in code and by collation in SQL (Low, unconfirmed)

`src/BillingRecon.Application/Receivables/OpeningBatchChecker.cs:44, 70, 212-218`,
`src/BillingRecon.Infrastructure/Billing/OpeningReceivables.cs:20-32`,
`src/BillingRecon.Infrastructure/Payers/ImportParties.cs:55-67`,
`src/BillingRecon.Application/Payers/ImportPartiesHandler.cs:181`

The duplicate checks use `StringComparer.Ordinal`; the unique indexes `UX_Bills_TenantId_LegacyNumber`,
`UX_Payments_TenantId_LegacyNumber` and `UX_Payers_TenantId_LegacyReference` compare by the column's collation. If
that collation is case-insensitive (the SQL Server default; not determinable by reading):

- A bills file with `OB-1` and `ob-1` passes the dry run and the submission with no finding. At approval the insert
  breaks the unique index, the unit of work answers 409 `duplicate_key`, and the batch can never be approved; no row
  or line is named.
- A bill row with `guarantor_ref` `abc` when the payer was imported as `ABC`: the query finds the payer, the ordinal
  dictionary does not, and the row is rejected as "not a guarantor here".

No money is wrong (the whole approval rolls back). Smallest fix: use `StringComparer.OrdinalIgnoreCase` for the three
`seen`/`before`/dictionary sets, so the code is at least as strict as the index.

## 5. Tests

### R11. The "at once" tests have no gate, so they pass when the two requests run one after the other (Medium)

`tests/BillingRecon.IntegrationTests/Database/CreditNotesApiTests.cs:418-436`,
`RefundsApiTests.cs:339-349`, `AdjustmentsApiTests.cs:306-316`, `BillPostingApiTests.cs:332`,
`CreditApplicationReversalsApiTests.cs:228-238`

Each starts two requests with `Task.WhenAll(Task.Run(...), Task.Run(...))` and accepts 409 or 422 for the loser. If
the first request commits before the second reads, the second is refused by the ordinary sequential check (422) and
the test passes without the lock having been exercised. Take `BR210_two_credit_notes_approved_at_once...`: delete the
second cap check under the lock (`ApproveCreditNoteHandler.cs:116-120`), the defect the test is named for, and the test
still passes on every run in which the requests do not overlap between lines 93 and 108.

`PaymentAllocationsApiTests.cs:255-257` and `BillApprovalApiTests.cs:498` show the right shape: a gate holds the first
request at the point of interest until the second has read.

Smallest fix: give each of these tests the same gate (a decorated `IReceivablesLedger` or `INumberSeries` in the
factory), so the second request has provably read before the first commits, and assert 409 exactly.

### R12. "The second taker waits" is asserted by a 750 ms sleep (Low)

`tests/BillingRecon.IntegrationTests/Database/NumberSeriesOnSqlServerTests.cs:250-251, 415, 436`; also `:315`

`Task.WhenAny(second, Task.Delay(750 ms))` then "second has not finished". On a loaded machine the second task may not
have reached SQL Server within 750 ms, and the assertion holds although nothing waited on a lock: a false pass, never a
false failure. Line 315 sleeps 500 ms and hopes the seven tasks have started.

Smallest fix: before asserting, poll `sys.dm_tran_locks`/`sys.dm_os_waiting_tasks` (the fixture has a privileged
connection) until the second session is seen waiting on the `NumberSeries` key, then release the first.

### R13. Assertions that count rows without the tenant (Low, unconfirmed)

`tests/BillingRecon.IntegrationTests/Database/RefundsApiTests.cs:362-365`

`SELECT COUNT(*) FROM dbo.Refunds WHERE [Status] = 'Posted' AND [Number] = 'REF/26-27/000001'` and the three counts
after it have no `TenantId`. They are right only if no other tenant in the same database has posted its first refund,
that is, if the class owns a clean database. Whether the fixture guarantees that could not be settled by reading; if
it does not, the test passes or fails by the order of the tests. Smallest fix: add `AND [TenantId] = @tenant`.

### R14. The audit-trail permission test covers two entity types (Low)

`tests/BillingRecon.IntegrationTests/Database/PermissionMatrixApiTests.cs:255-282`

`US43_every_role_reads_the_trail_of_a_patient_but_only_a_tenant_admin_reads_the_trail_of_a_user` checks `Patient` and
`User`. It cannot see R7: no case asks for the trail of an `Adjustment` as Cashier or of a `Refund` as BillingClerk.
The matrix walk above it (`:219`) checks each route once with an empty request, so it sees the route's policy and
nothing that depends on a query value. Smallest fix: a theory over (entity type, role) with the expected answer taken
from the same `Matrix` table.

## What was checked and found sound

**Money**

- Every posting use case (post bill, approve bill, record payment, allocate, approve credit note, apply credit,
  approve adjustment, approve allocation reversal, approve payment reversal, approve credit-application reversal,
  approve refund, approve opening batch) writes the document, the ledger posting and the payer's cached balances in one
  transaction; a refusal after the number was taken returns a 4xx and `IdempotencyStore.RejectAsync` rolls the
  transaction back, a fault releases the key and rolls back, so a number cannot stay taken without its document. All
  number-taking actions carry `[Idempotent]`.
- Two allocations of the last rupee: both change the payment row (same payment) or the bill row (two payments, one
  bill) under `rowversion`, and `PayerBalances` is read `UPDLOCK`; the loser gets 409.
- Two refunds of the same cash or the same credit: both change the source row under `rowversion`.
- Two credit notes over a bill's remainder when the bill row is not touched (bill fully paid): the first ledger post
  takes the `UPDLOCK` on the payer's balances, and the cap is read again after it (`ApproveCreditNoteHandler.cs:116`);
  different fiscal-year series do not open a gap because the payer lock, not the series lock, serialises them. Sound by
  reading under READ COMMITTED; not run.
- An approval racing a change: a pending bill, credit note, adjustment or refund cannot be edited or voided
  (`RefuseUnlessDraft`); an approval and an allocation on the same bill meet on the bill's `rowversion`; a refund and a
  payment reversal exclude each other through `Payment.Status` and `AnyPostedFromPaymentAsync`, so the throw at
  `Payment.cs:556` is not reachable.
- A second approval or post of the same document under another key: stopped by `If-Match` (428 without, 409 stale).
- The opening batch: content hash unique among live batches; the files are checked again at approval; two different
  batches naming the same legacy bill are stopped by the filtered unique indexes on `LegacyNumber`; opening advances
  cannot be reversed.
- Line arithmetic rounds per line with `MidpointRounding.AwayFromZero`; `Money.Of` refuses sub-paisa digits; ledger
  postings are checked balanced and one-sided in the domain.

**Tenancy**

- `IgnoreQueryFilters`: one use, `LoginUserLookup.cs:31`, with an explicit `TenantId ==` on the tenant found by code.
- Raw SQL: `NumberSeriesAllocator` (2), `ReceivablesLedger.MoveBalances`, `LedgerMovementsQuery` (2),
  `ReconciliationQuery`; every statement is parameterised and carries `[TenantId] = @tenant` from `ITenantContext` on
  every table it reads or writes. `DatabaseSettingsProbe` opens a connection for server settings only.
- All 26 entity types implement `ITenantScoped` (or are the tenant row) and get the query filter by convention; the
  write guard stamps and checks the tenant on every insert, update and delete.
- Image endpoints: `TenantImage` is tenant-scoped, looked up by kind and hash inside the filter, and the hash comes
  from the caller's own tenant row. Print settings, the two `recorder` endpoints (payment first, then the user name,
  both filtered), `imports/parties` and `opening-batches` read and write only through the filtered context.
- Cross-tenant references by id (patient, payer, service item, bill of a credit note, adjustment or allocation, source
  of a refund, patient of a payer, printed document) are all resolved through filtered queries before use.
- Idempotency keys are keyed `(TenantId, Key)` and read through the filter.

**Authorisation**

- Each controller action was compared with the matrix of `docs/requirements.md` section 1; apart from R7 and R8 the
  policy on each is the one the matrix gives. There is a fallback policy requiring an authenticated user.
- A disabled user, a signed-out user, a user whose roles were replaced or whose password was reset: the next request
  fails, because `SessionGateMiddleware` reads status and `SessionVersion` from the database on every request and each
  of those actions raises the version. A suspended tenant's users keep access for at most 30 seconds per process
  (`TenantStatusCache.Lifetime`); sign-in refuses a suspended tenant at once. Token lifetime 60 minutes, 15 for a
  forced password change, which reaches only the two endpoints marked for it.
- JWT validation pins issuer, audience, HS256, signed and expiring tokens, a key of at least 256 bits, and refuses the
  development key outside Development; the development scheme is registered only in Development.
- Sign-in answers one generic refusal for unknown tenant, unknown user, wrong password and disabled user, and hashes
  in every branch.
- The maker cannot approve or reject his own request on any document type; every reject handler goes through the same
  check.

**Input**

- Image upload: the body is read to the limit plus one byte and no further; type is taken from the bytes (PNG, JPEG,
  WebP headers), not from `Content-Type`; SVG cannot pass; the answer is served with the sniffed type and `nosniff`.
  The JPEG segment walk always advances and is bounded by the buffer.
- CSV import parser (`CsvTable.cs`): quotes, doubled quotes, BOM, embedded newlines and an unterminated quote all end
  in rows, never in an exception; files and row counts are capped; amounts parse with `AllowDecimalPoint` only and the
  invariant culture; dates are exact `yyyy-MM-dd`.
- Search text: `LikePattern.Containing` escapes `\`, `%`, `_` and `[`; the two `string.Contains` uses
  (`PayerReadService.cs:45`, `BalanceReports.cs:41`) are translated by EF with its own escaping.
- Printed sheets: no `dangerouslySetInnerHTML`, `innerHTML` or `srcDoc` anywhere in `frontend/src`; letterhead and
  print-settings text reach the sheet as React text nodes; the two images are `<img src>` of fetched bytes.
- `frontend/src/reports/csv.ts`: every text cell, header, title and total label passes `guardText` (`= + - @ TAB CR`)
  before quoting; amount, date, instant and count cells are fed only from typed server fields.

## The ten to fix first

1. **R1** - the only path found where cash leaves for money never received while every identity still holds.
2. **R5** - one TenantAdmin can post a refund alone; it voids rule 9 for every document type.
3. **R2** - a lost answer plus a reload doubles a payment, and the copy is refundable.
4. **R6** - the threshold is the bill control and its own subject can switch it off.
5. **R7** - full document content to roles the matrix leaves blank, one GET away.
6. **R11** - the race tests would not notice if the locks behind R1's neighbours were removed.
7. **R9** - the author of an amount can be its checker; a two-line change beside the existing comparison.
8. **R3** - a crashed request leaves a key that answers 409 until the page is reloaded; the sweep is promised and absent.
9. **R8** - same leak as R7 through a report; one attribute.
10. **R10** - a go-live import that passes the dry run and then cannot be approved, with no row named.
